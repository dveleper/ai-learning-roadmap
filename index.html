De desarrollo backend a arquitectura de soluciones de IA

Ruta de seis fases para profesionales de software que quieren diseñar, construir y operar aplicaciones con IA generativa mientras desarrollan el inglés técnico para explicar sus decisiones.

Prerrequisitos recomendados

  • Haber construido o mantenido una API REST. Los laboratorios usan Java y Spring Boot.
  • Manejar Git y la terminal, y poder ejecutar pruebas en un proyecto local.
  • Contar con un computador, conexión a internet y un entorno de desarrollo Java.
  • Poder presentarte y entender instrucciones sencillas en inglés (A1–A2). El diagnóstico inicial orienta la práctica.

La ruta introduce la IA generativa desde los fundamentos. En las fases avanzadas usarás herramientas de IA y servicios de nube que pueden requerir cuenta y tener costos de uso.

Cómo seguir la ruta

Empieza por el diagnóstico de la fase 1 y usa el temario y sus entregables para planificar el estudio a tu ritmo. Cada sesión propone 60 minutos de clase o laboratorio y 20 de práctica oral en inglés.

Usa el calendario del portal como referencia, registra tus prácticas en la bitácora y revisa el hito de cada fase antes de avanzar. El calendario de Google corresponde a la programación original.

La meta de salida es defender una solución de IA de punta a punta y progresar hacia inglés B2. El nivel se comprueba con una evaluación independiente.

Plan de estudios

Las seis fases combinan temas técnicos, práctica de inglés y un entregable para demostrar lo aprendido.

Mensajería e integración XML y JSON

En la fase 1, valida una cotización en JSON y XML. Usa OpenAPI para describir la API REST, JSON Schema para validar JSON y XSD para validar XML. Con Jackson y JAXB, convierte ambos formatos al mismo modelo de dominio y prueba campos requeridos, importes inválidos y namespaces.

En la fase 2, integra un proveedor SOAP simulado mediante su contrato WSDL y transforma la respuesta XML en una cotización que la API devuelve en JSON. En las fases siguientes, publica un evento de emisión en Kafka y enruta un mensaje en RabbitMQ. Practica evolución de esquemas, idempotencia, reintentos y trazabilidad. Usa Claude Code para proponer casos de prueba y comprueba los resultados ejecutándolos.

    Laboratorio de despliegue de microservicios Java

    En la fase 3, despliega el mismo microservicio Spring Boot WebFlux primero en Kubernetes local y después, opcionalmente, en Amazon EKS. El ejemplo parte del Scaffold Clean Architecture público de Bancolombia y reproduce un flujo de entrega empresarial con un repositorio y datos de laboratorio.

    Ruta local sin costo de nube

    1. Genera el proyecto con el scaffold público. Agrega una API REST, un caso de uso, adaptadores y Actuator. Ejecuta ./gradlew clean build y valida los endpoints con pruebas automatizadas.
    2. Empaqueta en una imagen OCI con Docker Engine y un Dockerfile multietapa. Usa Docker Compose para levantar la aplicación y PostgreSQL. Agrega RabbitMQ si el ejercicio practica mensajería.
    3. Crea un clúster con kind, carga la imagen con kind load docker-image roadmap-api:local después de construirla con esa etiqueta, e instala el chart con helm upgrade --install roadmap-api ./helm/roadmap-api. Usa los valores locales del chart para esa imagen.
    4. Define Deployment, Service, configuración, probes y límites de recursos. Usa kubectl rollout status deployment/roadmap-api si el chart usa ese nombre, y prueba vía kubectl port-forward.
    5. Ejecuta el pipeline con Jenkins local o GitHub Actions según la cuota disponible. Agrega controles con SonarQube Community Build y Karate, y practica despliegue declarativo con Argo CD.
    6. Observa métricas con Micrometer, Prometheus y Grafana. Añade trazas con OpenTelemetry y revisa registros con kubectl u OpenSearch. Simula un fallo de aplicación, diagnostícalo y revierte la versión.

    Ruta opcional en AWS EKS y herramientas empresariales

    1. Usa una cuenta sandbox autorizada. Estima clúster, cómputo, red, registro y observabilidad. Configura alertas de presupuesto antes de aprovisionar. Consultar precios de EKS.
    2. Configura AWS CLI, kubectl y eksctl. Crea un EKS de laboratorio y un grupo de nodos siguiendo la guía de EKS con eksctl. Verifica el contexto, namespace y permisos antes de aplicar recursos.
    3. Publica la imagen con etiqueta de versión en Amazon ECR. Configura el pipeline con identidad federada y permisos mínimos. Apunta los valores de Helm al repositorio ECR y habilita el despliegue desde Argo CD.
    4. Prueba acceso con port-forward. Si necesitas tráfico externo, configura el controlador de balanceo, TLS y DNS en el sandbox. Practica secretos administrados, despliegue gradual y rollback.
    5. Si tienes acceso empresarial, repite el flujo con Azure DevOps Pipelines o Jenkins, SonarQube comercial, Dynatrace, IBM MQ para mensajería y OpenShift como variante de plataforma. Usa las guías del proveedor y las plantillas autorizadas de tu organización.
    6. Al finalizar, retira primero los servicios que crearon recursos de red y después elimina el clúster y los recursos del laboratorio. Comprueba que no queden balanceadores, volúmenes, registros, imágenes o recursos de red con costo.

    Consulta la AWS Training Library de EPAM si tienes acceso, o AWS Skill Builder para recursos públicos.

    Evidencia de cierre. Entrega un repositorio de ejemplo con Dockerfile, Compose, chart Helm, pipeline, pruebas, instrucciones de despliegue y rollback. Adjunta una captura de métricas y explica en inglés cómo diagnosticarías un fallo.
